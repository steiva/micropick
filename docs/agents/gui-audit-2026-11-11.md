# GUI audit, 2026-11-11

Audit of `src/micropick/gui/` (32,797 lines) at commit `218a634`, the code
of `ghent-gui` (1.1.0), written on branch `audit/gui`. Nothing in `src/` or
`tests/` was changed.

**The branch is cut from `audit/tests`, not from `main`.** `main` is 1.0.1
and lacks seven commits of the program (tip calibration by hand, the click
fix) and the test audit; the test audit's fixes are merged nowhere yet. The
report and its scripts are one commit and move to any base with
`git cherry-pick`.

Everything was run with the mock robot and the synthetic cameras
(`Options(mock=True)`), `MICROPICK_ROOT` in a scratch folder, Qt platform
`offscreen`, on an Apple M1, macOS 26.3, Python 3.14.3, PySide6 6.12. No
robot was moved and no camera opened. Rates and times on the Windows
laptop will differ; the causes will not. What only the bench can answer is
in section 5.

Each finding is **confirmed** (reproduced, measured, or an unambiguous code
path) or **suspected** (reasoning only). The scripts are in
`scripts/audit/gui/` (section 7); each one's docstring says how to run it.

## 1. Summary

1. **GUI-01. The program uses a whole processor core while it does
   nothing.** A side panel's scroll column measures itself again each time
   it has measured itself: about 2,400 passes a second, from the first
   second, on Home, hidden pages included. A two-line fix takes Home from
   100 % of a core to 1 %. Confirmed.
2. **GUI-02. On a computer with a decimal comma a typed `-0.5` is read as
   -5 and `0.5` as 5.** Every number field: heights, offsets, volumes, a
   point's Z, the picking settings. Five tests that show it are written.
   Confirmed for Dutch (Belgium); the Ghent laptop's own setting is a
   bench check.
3. **GUI-03. ↑ ↓ PgUp PgDn move the robot while a number or a name is
   being typed.** The pad says "Keys now control the input field, not the
   robot." at that moment. PgDn is Z down. Confirmed.
4. **GUI-04. The first Stop does not end a short job that has several
   moves.** Shake the dish made 10 more moves after Stop; Manual pick's
   Aspirate goes on down into the well. The toast says "Stopping after the
   current move." Only the second press stops it. Confirmed.
5. **GUI-05. A robot that stops answering in the middle of a command
   holds the program for good.** The robot client is made with no timeout,
   so the job never ends, every button stays gray, and the window refuses
   to close. Confirmed by the code; a bench check.
6. **GUI-06. A key or click handled just as a job ends takes that job's
   answer.** The panel is "not busy" before the job's end is delivered; the
   new job replaces it, and the first job's callback is then run with the
   second job's result. Confirmed with the order forced.
7. **GUI-07. Closing the window while a model loads, a detection runs or
   a picture is saved ends the process with a crash.** `closeEvent` waits
   for the robot only. Exit code -6, "QThread: Destroyed while thread is
   still running". Confirmed.
8. **GUI-08. A click on the picture moves the robot up to 0.4 s later,
   also when the page was left meanwhile.** Confirmed.
9. **GUI-09. An exception in a slot is written to the log and the operator
   is told nothing;** one in a job's callback leaves the pad gray.
   Confirmed.
10. **GUI-10. Every jog step redraws every page, the hidden ones too:**
    7.6 ms of the GUI thread inside the claim of the robot, before the move
    starts. Confirmed.

Looked for and not found: a widget touched from a worker's thread (all 53
connections to a worker's signals are bound methods of QObjects), a lease
not given back after a failure, a timer running for a hidden page (once
GUI-01 is fixed, nothing of a hidden page runs), a connection made again at
each show, widgets or memory growing with use, a file written in place.

### Threads

- **GUI thread.** All widgets; `Session` lives here.
- **One QThread per `Worker`** (workers/base.py:240): a jog step, a pose
  read, a `run_job`, a run (picking, liquid, camera sweep, tip
  calibration), a labware load, a camera open, a model load, a detection,
  a picture saved, the monitor's look, the lights. A worker holds itself in
  `_RUNNING` until its thread is destroyed. Its signals reach the GUI
  thread only through a bound method of a QObject: a lambda, a nested
  function or a `partial` connected to a worker's signal runs **on the
  worker's thread** (measured, `slot_threads.py`); a signal of the `Session`
  emitted from a worker reaches a lambda on the GUI thread.
- **One grab thread per open camera** (`hardware.camera.BackgroundCamera`),
  from the first page that shows it until `Session.shutdown`. It keeps
  running while Home is shown.
- **Clip writer and recorder threads** during a picking run with clips.

Session state is written from workers (`lights`, `tip`, `run_state`,
`_open`) without a lock except `_open_lock`; what the GUI reads of it is
told through signals.

### Where a frame arrives

`BackgroundCamera._loop` keeps the newest frame. `CameraView._tick` (30 Hz,
GUI thread) calls `camera.read()`, and if it is another array than the one
shown: crop, `cv2.resize`, `QImage`, `update()`. Nothing is queued; a frame
not asked for is dropped. A picking run hands a `PickView` to the page
through a signal and the page shows it every 100 ms (`_show_run_view`). The
tip calibration's boxes come through `frame_seen` (a signal). The marker
watch and the detections take `view.held_frame` on a worker.

## 4. Findings

### GUI-01. A scroll column measures itself without end
**High · A, event loop · confirmed.** `src/micropick/gui/theme/factory.py:436-457`.

`_ScrollColumn._fit_height` calls `layout.invalidate()` on the inner
widget's layout. On a layout that was activated, `invalidate` posts a
`LayoutRequest` to that widget. The column's `eventFilter` starts the
0 ms `_fit_timer` at every `LayoutRequest` of the inner widget, the timer
calls `_fit_height`, which activates the layout and invalidates it again.
Each pass asks for the next. The docstring says "It cannot loop: the
minimum is only written when it changes"; the minimum is not what loops.

Evidence. `fit_loop.py`: 2,228 passes in one second in the Tip step's
column, each asked for by a `LayoutRequest`, 2,228 of them changing
nothing. `cpu_idle.py`: table 3.1. It starts with the window (the Tip
step's column is laid out at start) and every column joins once its page
was shown, and stays in after the page is hidden. In the code since
`278f151` (2026-09-22).

What it costs: a core; the GIL, which every worker's Python waits for (a
run's analysis, the camera threads, the detection); the laptop's battery
and fan. The test suite is not faster without it (its waits sleep).

Fix. `_fit_labels` returns whether it changed a label's minimum height,
and `_fit_height` calls `layout.invalidate()` only then (variant A in
`fit_fix.py`). A pass that changes nothing then posts nothing. Variant B
keeps the code and takes the pass's own request back with
`QCoreApplication.removePostedEvents(self._inner, QEvent.Type.LayoutRequest)`.
Both were applied from outside `src/` (`-p fit_fix`). The ten GUI test
files that lay out columns pass with either (546 tests). The whole suite
on 6 workers: 1,839 passed with B; with A 1 failed,
`test_dish_bottom.py::test_measured_with_the_tip`; with neither 1 failed,
`test_camera_calibration_sheet.py::test_the_sweep_is_a_run_with_stop_and_the_pill`.
Both are flaky tests the test audit names (its causes A and C); neither
was run again alone. Correct the docstring.

Test: `tests/gui/test_scroll_column.py::test_a_column_that_changes_nothing_measures_itself_no_more`:
a `scroll_column` with one wrapped label, shown; after 0.2 s of events,
count `_fit_height` calls over the next 0.2 s: 0. And
`test_a_longer_text_is_still_given_its_height`: `setText` of three lines,
events, the label's `minimumHeight` is the three lines'.

### GUI-02. A typed number is misread on a computer with a decimal comma
**Critical where the computer has a comma (a height sent to the robot) · E, C · confirmed for the locale, the laptop's setting not checked.**
`src/micropick/gui/app.py:47-72` (no `QLocale` is set);
`theme/factory.py:276` (`_NumberField`), `widgets/settings_form.py:99-117`,
`widgets/point_list.py:249-300`.

Every number is typed into a `QDoubleSpinBox`, which reads by Qt's default
locale: the system's. In Dutch (Belgium) the point is the thousands sign
and is dropped.

Evidence: `scripts/audit/gui/test_comma_locale.py`, 4 of 5 fail:

| Field | Typed | Read |
|---|---|---|
| `number_field` (Amount, Speed, Z, Above the bottom) | `1.5` | 15.0 |
| a signed one (Dispense's Offset) | `-0.5` | -5.0 |
| a picking setting (`settings_form._number`) | `0.5` | 5.0 |
| a point's Z in Points | `47.5` | 47.0 (the 5 would pass the field's range and is refused) |

This is the test audit's G-01, here with what the robot is given. The
fields then also show `1,50` while every label, toast and file says `1.5`.
Nothing else parses a number the operator types (`float(text)` is not used
on input under `gui/`); JSON and the liquid run's CSV are written by Python
and are the same on any computer.

Fix. `QLocale.setDefault(QLocale.c())` in `create_app` before the first
widget, and in the tests' `app` fixture. Then decide the comma: under the
C locale `1,5` is refused as it is typed (the key does nothing), which is
safe; accepting it as the decimal sign needs a `validate`/`valueFromText`
on the three field classes. Keep `QLocale.c()` with
`QLocale.NumberOption.RejectGroupSeparator` so `1,5` can never be 15.

Test: the five in `test_comma_locale.py`, moved to
`tests/gui/test_number_locale.py`, plus one that `create_app` leaves
`QLocale().decimalPoint() == "."`.

### GUI-03. ↑ ↓ PgUp PgDn move the robot while a field has the keyboard
**High · C, robot safety · confirmed.**
`src/micropick/gui/widgets/jog_panel.py:384-417` (shortcuts), `698-705`
(`_focus_moved`), `909-930` (`_set_enabled`).

The jog keys are window shortcuts. Qt asks the focused widget first
(`ShortcutOverride`), and a line edit keeps only the keys it edits with:
characters, Left, Right, Home, End, Backspace, Delete. Up, Down, PgUp and
PgDn it does not claim, in a spin box neither, so the shortcut takes them.
`_focus_moved` sets `_typing` and changes the pad's text; it does not turn
the shortcuts off.

Evidence: `keys_in_field.py`, Manual pick's Run, a tip on:

| The keyboard is in | Left, Right | Up, Down | PgUp, PgDn | + - U A D R |
|---|---|---|---|---|
| In place's amount (a number field) | the field's | **robot moved** | **robot moved** | nothing |
| a point's name (a line edit) | the field's | **robot moved** | **robot moved** | typed |

The pad shows "Keys now control the input field, not the robot." all the
while. CLAUDE.md: "A text or number field with the keyboard keeps the keys
it uses (never taken from it: the robot would move while a digit is
corrected)", and a number field steps with ↑/↓ "only with the keyboard":
it never gets them on a page with a pad. The step is the pad's, up to
10 mm.

Fix. In `_set_enabled`, a shortcut is enabled only while
`not self._typing`; `_focus_moved` calls `self._set_enabled(self._worker is None)`
when `_typing` changes. The keys then reach the field (↑/↓ step it) and
come back with Enter or a click, as the pad says. Leave H.

Test: `tests/gui/test_movement_keys.py::test_no_jog_key_moves_the_robot_while_a_field_has_the_keyboard`
(parametrized over Up, Down, PgUp, PgDn and over `in_place_amount` and a
point's name editor: `robot.moves` unchanged), and
`test_up_steps_the_number_field_on_a_page_with_a_pad` (the value changed).

### GUI-04. The first Stop does not end a short job between its moves
**High · C, robot safety · confirmed.**
`src/micropick/gui/widgets/jog_panel.py:497-531` (`run_job`),
`workflows/motion.py` (no stop anywhere),
`pages/manual.py:1450-1456, 1523-1535, 1620-1626`, `pages/picking.py:654-663`.

A job given to `JogPanel.run_job` runs to its end. `Motion` takes no stop,
the panel does not listen to `Session.stop_requested`, and Manual pick's
`_stop` only ends a wait before a lift. Such a job is several moves: By
clicking's Aspirate is the camera to the spot, the tip across, down,
aspirate, up, back; Shake the dish is the tip into the dish, the stir's
strokes, and back.

Evidence: `stop_in_job.py`. Shake the dish on a mock moving at 100 mm/s,
Stop pressed during the first move: "moves made before Stop: 1; after
Stop: 10", the last toast "Dish shaken.", and the toast at the press
"Stopping after the current move. Press Stop again to hold the robot."

The second press within 10 s holds the robot and does stop it. So an
operator who sees the tip going to the wrong place has to know to press
twice, against what the screen says.

Fix, to decide with the user (it changes what a short job does):
`Session` keeps a `threading.Event` set by `request_stop` and cleared by
`JogPanel._run` when a job that is not a run starts. `Motion` checks a
stop given for the calling thread at the start of each move
(`with motion.stopping_on(event):` around `fn(log)` in `run_job`'s job,
kept in a `threading.local`, so a run's own thread is not touched) and
raises a `Stopped` whose text is "Stopped: the tip stays where it is.".
The least there is to do without that decision: the first press says
"Stop: this job cannot be cut short. Press Stop again to hold the robot."
while the lease's holder is not a run.

Test: `tests/gui/test_stop.py::test_stop_ends_a_short_job_after_the_move_in_progress`:
a `run_job` of three `motion.tip_to` on a mock with `speed_mm_s=100`, Stop
during the first, `robot.moves` grows by at most one, the toast is the
stopped sentence, the lease is free.

### GUI-05. A robot that stops answering during a command holds the program
**High · F, B · confirmed by the code path; not run (needs the robot).**
`src/micropick/gui/session.py:1157` (`OpentronsAPI(host=..., port=...)`,
no `timeout`), `src/opentrons_api/ot2_api.py:84-94` ("None waits as long as
the robot takes"), `src/micropick/gui/shell.py:404-415`,
`session.py:2101-2106, 2454`.

With the cable pulled or the robot frozen while a command is being waited
for, `requests` waits without end. The worker never ends, so the lease is
never given back: every jog panel and button is gray, the first Stop has
nothing to stop at, the second only refuses later commands. `closeEvent`
waits 10 s, says "Not closed: the ... is still stopping. Close again once
it has." and never closes: the program has to be ended from the Task
Manager.

At close with a robot that no longer answers, `Session.shutdown` calls
`retract_axis` on the GUI thread, with no timeout: the window stands
frozen for as long as the network takes to give up.

Fix. A connect timeout and TCP keep-alive on the client's connection
rather than a read timeout: a slow dispense or a home is a long read that
is right. `OpentronsAPI(timeout=(5, None))` and a `requests` adapter that
sets `SO_KEEPALIVE` (idle 10 s, interval 5 s, 3 probes), so a dead peer
ends the read in about half a minute with a `ConnectionError`, which
`describe_error` already says in words. In `closeEvent`, after the wait,
offer "Close anyway" (cameras closed, no retract). `shutdown`'s retract on
a worker with a wait of a few seconds.

Test: `tests/gui/test_shell.py::test_close_is_offered_when_a_job_never_ends`
(a `run_job` blocked on an event; close, wait patched to 0.2 s: the
question is asked; "Close anyway" closes). The keep-alive itself is bench
check 5.3.

### GUI-06. A job started as another ends takes the other's callback
**Medium · B, race · confirmed with the order forced; how often is not measured.**
`src/micropick/gui/widgets/jog_panel.py:575-576` (`_busy`), `515-531`,
`613-643`.

`_busy()` is "the worker's thread is running". The thread ends before
`_job_done` is delivered on the GUI thread, and a key, a click or a timer
handled in that gap finds the panel free (`job_pending` is True then,
`busy` False). `_run` replaces `_worker`; the first job's `_job_done` is
